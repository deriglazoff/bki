# Волна A: карточка договора (ОЧ)

Цель: сотрудник не сверяет три бюро руками, если факты однозначны. Не AI — явные правила.

## Схема карточки

```json
{
  "case_type": "ОЧ",
  "from_file": {
    "fio": null,
    "uid": null,
    "passport": null,
    "pd": null,
    "contract_id": null,
    "bureau": "НБКИ|ОКБ|Эквифакс"
  },
  "from_po": {
    "found": true,
    "keyPart": null,
    "contract_status": "open|closed|terminated|sold",
    "dates": { "issue": null, "close": null },
    "overdue": { "present": false, "until": null },
    "pko": null,
    "bankruptcy": { "present": false, "date": null, "source": "Bankrot|null" }
  },
  "bureau_snapshot": {
    "NBKI": { "status": "open|closed|sold|bankrupt|missing|unknown", "note": null },
    "Equifax": { "status": "...", "note": null },
    "OKB": { "status": "...", "note": null }
  },
  "decision": {
    "rule_id": null,
    "action": "draft_refusal|draft_correction|escalate_B|escalate_human",
    "stop": [],
    "draft_hint": null
  }
}
```

Поля `from_file` заполняет общий парсер (как у ЗЗ). Поля `from_po` — обогащение из ПО. `bureau_snapshot` — сверка (на буткемпе заглушка или ручной ввод).

## Правила решения

Порядок важен: первое сработавшее правило побеждает.

| ID | Условие | Action | Черновик / стоп |
|----|---------|--------|-----------------|
| R1 | `from_po.found = false` или договора нет | `escalate_human` | Список недостающих идентификаторов. Не отказ. |
| R2 | `from_po.bankruptcy.present = true` | `escalate_B` | Не шаблонить ОЧ; передать в карточку Б. |
| R3 | Все три бюро в `bureau_snapshot` совпадают с `from_po.contract_status` (и просрочка/ПКО согласованы) | `draft_refusal` | «Информация в НБКИ/Экви/ОКБ отображается корректно». Можно «готовь ответ». |
| R4 | Расхождение по закрытию / продаже / статусу хотя бы в одном бюро | `draft_correction` | Черновик корректировочной выгрузки. **Стоп:** не отвечать клиенту, пока выгрузка не принята бюро. |
| R5 | Просрочка в ПО есть, в одном бюро отсутствует (или наоборот), без банкротства | `draft_correction` или `draft_refusal` по факту после сверки дат | Если даты сходятся с ПО → R3; иначе R4. |
| R6 | Иначе | `escalate_human` | Карточка фактов без выбора стороны. |

## Формулы ответа (из корпуса)

Типовые фразы сотрудников — эталон тона, не автоотправка:

- Корректно: «Информация по заявке и кредиту отображается корректно: договор …, есть/нет просрочки. Отправляю ответ на оспаривание.»
- По бюро: «НБКИ — … / Эквифакс — … / ОКБ — …»
- После выгрузки: «Выгрузка принялась без ошибок, информация о закрытии договора во всех БКИ отображается корректно.»
- ПКО: «Информация о продаже в ПКО „…“ отображается корректно: …»

## Вне скоупа волны A

- SQL-правки в ПО
- Автонумерация массовых выгрузок
- Автоотправка в бюро или клиенту
- Обучение модели на ОЧ (сначала правила + [och-gold-set.json](och-gold-set.json))
