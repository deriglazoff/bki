# Действия сотрудников: ОЧ и ТЧ

Разбор по человеческим комментариям задач с тегами **ОЧ** (449 с чатом) и **ТЧ** (258 с чатом).  
Источник: [../research/osparivanie-2026-tasks.csv](../research/osparivanie-2026-tasks.csv) + [../research/osparivanie-2026-comments.csv](../research/osparivanie-2026-comments.csv). Сырые корзины: [actions-och-tch-raw.json](actions-och-tch-raw.json).

**Важно:** правка в ПО через UI часто **не пишется** в чат (нет SQL). Поэтому три уровня сигнала:

| Уровень | Что видно в чате | Интерпретация |
|---------|------------------|---------------|
| **Явная правка БД/ПО** | SQL (`UPDATE`/`INSERT`/`DELETE`), «поменял поле», PrichStat, удалил паспорт из базы | Точно трогали нашу БД |
| **Корректировка в бюро** | массовая выгрузка / «отправил корректировки» без SQL | В БКИ данные меняли; ПО могли поправить молча или только переотправить событие |
| **Без изменения данных** | «отображается корректно» → ответ | Ни БД, ни выгрузку не делали — только сверка и ответ |

## ОЧ — что делают

### 1. Без изменения нашей БД (основной объём)

Действия = сверка ПО ↔ 3 бюро → формула ответа → «готовь ответ» / направил ответ.

| Подтип | Доля* | Действие сотрудника | Пример |
|--------|------:|---------------------|--------|
| Ответ без развёрнутой сверки в чате | ~37% | Закрыл процесс ответом (детали могли быть в файле) | «направил ответ» |
| Корректно — общее | ~12% | Сверил, отказал в оспаривании | «Информация отображается корректно» |
| Корректно — просрочка | ~6% | Подтвердил открытый договор + просрочку | «договор открыт, есть просрочка» |
| Корректно — закрытие | ~4% | Подтвердил закрытие во всех БКИ | «договор закрыт… корректно» |
| Корректно — банкротство (тег ОЧ) | ~4% | Сверил дату банкротства vs просрочку | «просрочка только до даты признания» |
| Корректно — ПКО | ~2% | Подтвердил продажу | «продажа в ПКО… корректно» |
| Промежуточный | ~3% | Ждёт бюро / коллегу | «промежуточный» |

\*Доли от задач ОЧ с комментариями; корзины взаимоисключающие по правилам бакетера.

**Автоматизация волны A:** именно этот блок — шаблон сверки 3 бюро без AI и без записи в БД.

### 2. Меняли данные у бюро (выгрузка), явной правки БД в чате нет

| Подтип | Доля | Действие | Пример |
|--------|-----:|----------|--------|
| Только корректировка | ~10% | Массовые в НБКИ/Экви/ОКБ | «Направил корректировки НБКИ - 66506…» |
| Корректировка → потом «корректно» | ~9% | Выгрузка, дождался приёма, ответил | «выгрузка принялась… корректно» |

Частые поводы выгрузки в ОЧ (по текстам):

- в одном бюро **нет договора / нет закрытия / нет продажи**, в ПО есть;
- нужно дослать статус (в т.ч. банкротство как код статуса);
- переотправка от другой организации (Саммит vs ПКО).

**Наша БД:** в чате почти не видно. Либо данные в ПО уже были верные (только досылка в БКИ), либо поле поправили в UI без SQL в комментарии. Явный SQL/смена поля — единицы (ниже).

### 3. Явная правка нашей БД (редко, ~1%)

Примеры из корпуса:

- смена `PrichStat35` в `DogovorCred` (причина статуса → банкрот);
- правки, связанные с таблицей `Bankrot` / статусом договора.

Дальше почти всегда идёт **корректировочная выгрузка** в бюро.

**Для автоматизации:** не цель волны A. Эскалация человеку / контур Б.

### Схема ОЧ

```text
входящее ОЧ
    │
    ├─ сверка: ПО == 3 бюро ──────────────► ответ «корректно»     [без БД]
    │         (просрочка / закрыт / ПКО / банкрот-дата)
    │
    ├─ в бюро дырка, в ПО ок ─────────────► массовая выгрузка       [БД обычно нет]
    │                                       └─► ждать приём ► ответ
    │
    └─ в ПО неверный статус/поле ─────────► правка ПО (+SQL редко) [БД да]
                                            └─► выгрузка ► ответ
```

## ТЧ — что делают

### 1. Явная правка нашей БД (~16% задач с явным сигналом)

Что правят (по упоминаниям в тех же задачах):

| Объект в БД | Как видно в чате | Дальше |
|-------------|------------------|--------|
| Паспорт (текущий / старые в `Partner_OldPasp`) | DELETE/INSERT OldPasp, «удалил паспорт» | корректировки во все БКИ |
| Адрес / место рождения | `UPDATE Partner SET …` | массовые выгрузки |
| Email / телефон | `UPDATE … [Электронная почта]` | иногда «удаление почты» в БКИ |
| ФИО | реже явный SQL; чаще «исправили в связанной задаче» | выгрузка |
| Исключение / событие 3.1 | «удалил целиком информацию о клиенте» | переотправка |

Типичный цикл ТЧ с БД:

1. Найти расхождение письмо ↔ ПО ↔ бюро  
2. Поправить Partner / OldPasp  
3. Сформировать массовые корректировки  
4. Часто — **промежуточный ответ**  
5. Дождаться приёма → официальный ответ  

### 2. Корректировка в бюро без SQL в чате (~52%)

Самая большая корзина ТЧ. Сотрудник пишет номера массовых (71136…) или «отправил корректировки», но UPDATE в чат не кладёт.

Интерпретация (осторожно):

- **часто** ПО уже поправили через интерфейс / ранее;
- **иногда** только переотправка события в БКИ при «в ПО всё верно»;
- **иногда** письмо в бюро без правки («нет точной информации — написал в НБКИ»).

Для плана: считать отдельным классом **«изменение витрины БКИ»**, не смешивать с доказанной правкой нашей БД.

### 3. Без изменения нашей БД и без выгрузки (сверка / отказ)

| Подтип | Действие |
|--------|----------|
| «отображается корректно» | Титул в ПО и БКИ совпадает с оспариванием → ответ |
| «исправлять не надо» | Нет фото нового паспорта / данные старые / в бюро уже ок |
| Уже исправлено в связанной задаче | Не дублировать правку; сразу ответ |
| Только процесс | промежуточный / «готовь ответ» без описания сути |

Доля «чистой сверки» в ТЧ заметно меньше, чем в ОЧ (~6–8% явных `verify_ok` без выгрузки vs ~30%+ в ОЧ).

### Схема ТЧ

```text
входящее ТЧ
    │
    ├─ уже правили в связанной задаче ───► ответ                    [без БД]
    ├─ ПО и БКИ ок ──────────────────────► ответ «корректно»       [без БД]
    │
    ├─ ПО ок, БКИ криво ─────────────────► выгрузка (± письмо)     [БД нет / спорно]
    │                                       └─► промежуточный ► ждать
    │
    └─ ПО криво ─────────────────────────► правка Partner/OldPasp  [БД да]
                                            └─► выгрузка ► промежуточный ► ответ
```

## Сводная матрица «действие → нужна ли наша БД»

| Действие | ОЧ | ТЧ | Наша БД | БКИ (выгрузка) |
|----------|:--:|:--:|:-------:|:--------------:|
| Сверка + «корректно» + оф. ответ | часто | редко | нет | нет |
| Сверка закрытие / просрочка / ПКО / банкрот-дата | часто | редко | нет | нет |
| Досылка договора/статуса массовой | средне | — | обычно нет | да |
| Правка статуса договора / Bankrot / PrichStat | редко | — | **да** | да |
| Правка паспорта / адреса / ФИО / email в Partner | — | часто* | **да** | да |
| Чистка `Partner_OldPasp` | — | да | **да** | да |
| Массовая корректировка титула (без SQL в чате) | редко | очень часто | ? | да |
| Промежуточный ответ | редко | часто | нет | нет (ожидание) |
| «Уже исправили в связанной» | — | да | нет (сейчас) | нет |
| Уточнение у коллеги / юр. | редко | редко | нет | нет |

\*«часто» среди задач, где правка вообще нужна; в абсолюте явный SQL ~16% ТЧ, плюс большая серая зона выгрузок.

## Выводы для автоматизации

**ОЧ**

1. Приоритет: сценарии **без БД** — карточка сверки 3 бюро и черновик «корректно».  
2. Второй слой: черновик **массовой выгрузки**, когда в ПО ок, в одном бюро пусто/старый статус.  
3. Правки нашей БД в ОЧ не автоматизировать.

**ТЧ**

1. Разделить assistive-подсказки:  
   - «ПО ок → только выгрузка / письмо в бюро»  
   - «ПО криво → нужна правка карточки» (флаг, **без** генерации SQL)  
   - «уже правили в задаче N → только ответ»  
2. Промежуточный ответ — штатный шаг при любой выгрузке.  
3. Серую зону «выгрузка без SQL» в метриках учитывать отдельно от доказанных UPDATE.

Пересчёт корзин: данные в [actions-och-tch-raw.json](actions-och-tch-raw.json).
