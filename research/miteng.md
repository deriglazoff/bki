## 📌 Основные темы:

### Тема 1: Что именно автоматизировать в первую очередь

- Обсуждалась автоматизация обработки **оспариваний**.

- Основной докладчик предложил начать с самого простого сценария:

 - **оспаривание на удаление запросов КИ**,

 - где сотрудник по сути готовит файл на удаление и отправляет его.

- Отмечено, что это наиболее безопасный и понятный для старта кейс.

- Более сложные кейсы, связанные с **проверкой кредита / договора**, содержат много нюансов:

 - клиента могут не найти,

 - нужно сверять статус кредита,

 - просрочки,

 - факт закрытия,

 - возможны неоднозначности.

**Вывод по теме:**

- В качестве первого этапа/буткемп-цели приоритет отдан **автоматизации удаления запросов**, а не полной автоматизации всех типов оспариваний.

---

### Тема 2: Какие данные нужно извлекать из входящих файлов

- Обсуждалось, что постановка задачи сейчас строится на данных из файлов, приходящих в разных форматах.

- Из файлов нужно уметь вытаскивать:

 - **ФИО**

 - **UID**, если есть

 - **паспортные данные**

- Если UID отсутствует, предполагается поиск клиента по:

 - ФИО

 - паспортным данным

- Также обсуждалось, что далее может понадобиться **хранимка / подтягивание данных из ПО**, чтобы обогащать задачу дополнительной информацией по клиенту.

**Риски / ограничения:**

- Не во всех документах есть UID.

- Некоторые PDF — это не текст, а **скан/картинка**, значит нужен OCR.

- Форматы документов различаются.

---

### Тема 3: Подход к парсингу документов

- MIC отметил, что не видит принципиальной проблемы в парсинге:

 - можно использовать библиотеки,

 - регулярные выражения,

 - AI/LLM,

 - морфологические признаки русских слов для распознавания ФИО.

- Для сканов потребуется OCR.

- Участники сошлись на том, что начинать можно постепенно, по мере накопления форматов.

**Вывод по теме:**

- Парсинг признан технически реализуемым.

- Требуется собрать больше примеров файлов по разным бюро и сценариям.

---

### Тема 4: Нужно ли только ставить задачу или сразу извлекать максимум информации

- SYSTEM изначально склонялась к более узкому scope: автоматизировать **создание задачи**.

- MIC настаивал, что нужно сразу вытаскивать **максимум информации из файла**, чтобы дальше не работать вручную с файлами.

- Обсуждалось, что в задачу можно прикладывать:

 - данные клиента,

 - сведения о договоре,

 - результаты проверки по базе,

 - шаблон ответа / файл для бюро,

 - возможно, рекомендации сотруднику, что делать дальше.

**Вывод по теме:**

- Предпочтительный вектор — не просто создать задачу, а **максимально наполнить её данными**, чтобы сократить ручную работу.

---

### Тема 5: Разделение простых и сложных кейсов

- Обсуждалась идея:

 - **80% типовых кейсов** (например, удаление запросов) автоматизировать максимально,

 - **20% сложных кейсов** анализировать отдельно и помогать сотруднику рекомендациями.

- Рома предложил использовать внутренний AI для анализа файла и выдачи типового решения.

- MIC поддержал идею:

 - собрать базу исторических задач,

 - категоризировать кейсы,

 - подбирать типовое решение по аналогии.

**Вывод по теме:**

- Для сложных кейсов рассматривается формат **assistive automation**:

 - не полная автоматизация,

 - а подсказка/гайд/типовое решение для сотрудника.

---

### Тема 6: Процесс удаления запросов и зависимость от ответа бюро

- Текущий процесс:

 1. приходит оспаривание,

 2. сотрудник готовит файл на удаление запросов,

 3. файл отправляется в бюро,

 4. приходит подтверждение от бюро,

 5. только после этого готовится ответ на оспаривание.

- Важный момент:

 - автоматизация должна учитывать, что ответ клиенту/по почте нельзя формировать до подтверждения от бюро.

- Также есть различия между:

 - обычными запросами,

 - запросами **SSP**,

 - разными бюро (НБКИ, ОКБ, Equifax и др.).

**Вывод по теме:**

- Автоматизация должна учитывать **многошаговый жизненный цикл** и ожидание внешнего ответа.

### Тема 7: Архитектура решения

- SYSTEM подняла вопрос архитектуры:

 - как связывать оспаривание, задачу, отправленный файл и входящие ответы,

 - как мониторить почту,

 - как понимать, к какому оспариванию относится письмо,

 - как не плодить лишние сервисы.

- Обсуждалось, что пока архитектура детально не проработана.

- MIC предложил на первом этапе сосредоточиться на:

 - скачивании файлов,

 - распознавании,

 - постановке задачи,

 - а более сложную связность и мониторинг развивать дальше.

**Статус:**

- Архитектура признана важной, но пока **требует уточнения / дальнейшей проработки**.

### Тема 8: Распределение работ на буткемпе

- SYSTEM обозначила проблему:

 - работы много,

 - сроки сжатые,

 - не до конца понятно, как делить задачи между участниками.

- Обсуждались варианты:

 - делить по бюро,

 - делить на входящий/исходящий контур,

 - выделить людей на архитектуру,

 - выделить людей на парсинг и скачивание файлов.

- Упоминалось:

 - Артур и Серёга могут заниматься реализацией,

 - возможна работа по бюро,

 - кто-то может заниматься UID/поиском данных,

 - кто-то — архитектурой или формированием ответов.

**Статус:**

- Полное распределение ролей в разговоре не зафиксировано окончательно.

- Артур запросил примеры файлов:

 - НБКИ,

 - ОКБ,

 - кейсы только на удаление запросов,

 - кейсы, где одновременно есть запросы и проверка кредита.

- SYSTEM пообещала:

- MIC предложил выгрузить большой массив писем/файлов для категоризации.

**Вывод по теме:**

- Сбор датасета примеров — один из ближайших шагов.

### Тема 10: Демо и ожидаемый результат буткемпа

- Обсуждалось, что нужно показать по итогам двух дней.

- Предварительное видение демо:

 - письмо попадает на почту,

 - система парсит вложения,

 - создаёт задачу,

 - прикладывает нужные данные / шаблонный файл / описание,

 - возможно, формирует ответ или заготовку ответа.

- Для демонстрации, вероятно, будет использоваться:

 - тестовая среда,

 - заглушки,

 - либо уже решённый кейс как пример.

- Отдельно обсуждалась необходимость показать **ценность**:

 - долю таких кейсов,

 - сколько сотрудников занято,

 - сколько рутинной работы можно снять,

 - потенциальную экономию человеко-часов.

## ✅ Принятые решения:

1. **Фокус буткемпа** — автоматизация работы с оспариваниями, в первую очередь **удаление запросов КИ**.  

  Срок: в рамках ближайшего буткемпа

2. **Не брать в первый приоритет полную автоматизацию кейсов по кредитам/договорам**, так как там много нюансов.  

  Срок: не указан

3. **Собирать максимум данных из входящих файлов** для наполнения задачи, а не ограничиваться только её созданием.  

  Срок: в рамках проектирования/реализации

4. **Собрать примеры файлов и кейсов** по разным бюро и типам оспариваний.  

  Срок: сегодня–завтра / требует уточнения по точной дате

5. **Для сложных кейсов рассмотреть AI-помощь**: категоризация, типовые решения, рекомендации сотруднику.  

  Срок: не указан

6. **Для демонстрации использовать тестовый/заглушечный сценарий или уже решённый кейс**, если нельзя показать реальный живой поток.  

  Срок: к демо буткемпа
