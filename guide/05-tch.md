## Откуда брать верные данные

Порядок:

1. Актуальное ФИО и паспорт в ПО — SQL [09-sql.md](09-sql.md) §2–3 (`Partner.keyFIO`, не история).
2. Фото паспорта на карточке клиента в ПО.
3. Если фото нет — заявление бюро (ФИО, паспорт) и сканы в хвосте Вх.
4. ИНН: кнопка «ИНН» на карточке → сайт ФНС по **текущему** паспорту из ПО.
5. СНИЛС без цифр от клиента: чат **СБ+Верификаторы**, сотруднику ОВиА, который сейчас в сверке (пишет «+» / «можно продолжить»). Если всё равно нет — **удалить** СНИЛС кнопкой «нет» на форме (не выдумывать).

**Сначала сверка, потом 3.1.** Если актуальное ФИО/паспорт/адрес уже как в заявлении (клиент пишет «Эривовна», в ПО уже «Эриковна»; просит дату 17.02, в ПО уже 17.02; в истории «Алиткачева», актуально «Алипкачева») — в `@answer` подтвердить текущие ПДн **явно**, выгрузку 3.1 не открывать, пока ЛК не покажет старое.

Не править карточку вслепую, пока не создана «грязная» выгрузка со старыми данными (см. золотое правило). Это только если ПО **неверно**.

## Золотое правило события 3.1

Выгрузки БКИ — это события. Титул правят событием **3.1**.

Чтобы 3.1 собралось, нужна **последняя** выгрузка по этому клиенту от **нужной организации в нужное бюро** в статусе «отправлено», и в ней уже заполнен блок, который правим.

План всегда такой:

1. Выгрузка с **текущими (неверными)** данными, статус **21 отправлено**.
2. Проверить таблицы/XML: в блоке именно ошибочные значения.
3. Исправить данные в ПО / таблицах.
4. Вторая выгрузка с **датой +1 день** — корректировочная.
5. Статус корректировки временно **23 отмена**, проверить событие **28** (= 3.1) в `KI_CreditHistoryList_Detail`.
6. Сменить дату события на **сегодня**, пересобрать XML, статус **13 готово к выгрузке**.
7. Отправить, дождаться приёма, **проверить ЛК** (принятый файл ≠ исправленный титул).
8. Пока ждём — промежуточный ответ.

Для **МКК ДЗБР**: дата по умолчанию 11.06.2011 на форме сменяется на **25.11.2014**. Корректировку ставить на **26.11.2014**. Статус первой выгрузки не 21, а **23**.

На **NewCP / тесте** перед выгрузками по договорам:

```sql
EXEC dbo.Dogovor_GP_Rasch @keyDZ = @keyDZ
EXEC dbo.RaschBalance
    @KeyDZ = keyDZ,
    @CurDate = '20240101',  -- меньше даты выдачи
    @ForTest = 1,
    @needSelect = 1
```

Иначе в FL27 и др. уедут нули/мусор.

## Универсальный процесс выгрузки 3.1

### Первая выгрузка (неверные данные)

Форма выгрузок: организация, бюро, тип **массовая**, даты **по умолчанию** (синий блок на скрине). В выгрузку — договор или заявка этой организации.

Сформировать сразу в «отправлено»:

```sql
EXEC KI_BKI_PrepareData @keyCHL = 52835, @needSelect = 1

UPDATE kul
SET Status = 21
FROM CZ_BKI..KI_UnloadList kul
WHERE kul.keyCHL = 52835
```

`keyCHL` — ключ расчёта на форме (выделить строку). Справочник статусов: `KI_UploadStatus_Config`.

### Вторая выгрузка (корректировка)

Сдвинуть дату в синем блоке **на 1 день**. Сформировать, статус **23**:

```sql
UPDATE kul
SET Status = 23
FROM CZ_BKI..KI_UnloadList kul
WHERE kul.keyCHL = 52835
```

Проверка 3.1:

```sql
SELECT TOP 100 *
FROM CZ_BKI.dbo.KI_CreditHistoryList_Detail AS KCHLD
WHERE KCHLD.keyCHL = 52852
-- нужно событие 28
```

Справочник событий: `CZ_BKI.dbo.KI_sprEvent`. XML — скрипт «формирование файла БКИ» из вложений Word.

### Дата события = сегодня

Экви и ОКБ могут не принять 3.1, если `eventDate` раньше выдачи договора. Выгрузка при смене даты должна быть в статусе **отменена**.

Способ А: XML, блок `FL_Event_3_1`, поле `eventDate` = сегодня → подписать, шифровать, отправить вручную.

Способ Б:

```sql
SELECT TOP 100 *
--UPDATE KCHLD
--SET dtEvent = '03.10.2025 0:00:00.000'
FROM CZ_BKI.dbo.KI_CreditHistoryList_Detail AS KCHLD
WHERE KCHLD.keyCHL = 42857
-- AND KCHLD.keyCHLD = …  -- ключ записи с событием 28
```

Потом удалить старый XML из экспорта и пересобрать:

```sql
-- KI_NBKI_Export / KI_EquiFax_Export / KI_OKB_Export: DELETE по keyCHL
EXEC dbo.KI_BKI_Format_xml @keyKUL = 0  -- ID выгрузки (keyKUL), не keyCHL
```

Проверить XML, статус **13**.

### Заявка/договор не попадает в отбор

На NEW_CP править ХП (только если иначе выгрузка пустая):

- `KI_FL55_application_Fill`, регион «Заполняем данные о заявках»: условие на свой `keyRec`, копия INSERT в ELSE, в join вместо `DSH.Stat IN (6,16,32,47,54,55,1)` — свой `keyDZ`.
- `KI_GetEvent`, регион «Собираем все договора за период»: статусы из `Dogovor_StatH` добавить в ХП, если их там нет.

## По блокам

### FL1 / FL2 — ФИО

1. Карточка vs фото паспорта vs заявление. Не спешить жать «править».
2. Грязная выгрузка. Проверка:

```sql
SELECT TOP 100 * FROM CZ_BKI.dbo.KI_FL1_name WHERE keyRec = 42884
SELECT TOP 100 * FROM CZ_BKI.dbo.KI_FL2_prevName WHERE keyRec = 42884
```

3. В ПО кнопка «править» ФИО.
4. `Partner_Edit_FullName`: у неактуальных строк `forDel = -1`. Если предыдущего ФИО нет — у последней записи `FN_Type = 2` с NULL ФИО оставить `ForDel = 0`, остальные такого типа = -1.
5. `CZ_BKI.dbo.KI_History_FL1`: type 1 = FL1, type 2 = FL2; править актуальную (`edit_date` больше).
6. Корректировочная выгрузка, дата события, отправка.

### FL3 — место / дата рождения

Грязная выгрузка → `KI_FL3_birthInfo` по `keyRec` совпадает с тем, что бюро считает ошибкой → «править» в ПО → корректировка → 3.1 → дата → отправка.

### FL4 / FL5 — паспорта

Типовые правки: дата выдачи, код подразделения, одна цифра серии/номера — не путать со склейкой чужого паспорта ([06-zs.md](06-zs.md)).

Порядок тот же: грязная (статус 21) → правка ПО/forge → выгрузка дата+1 → 3.1 → статус 13.

Таблицы: `KI_FL4_id`, `KI_FL5_prevId`, `KI_History_FL4`, `Partner_OldPasp` (расшифровка `f_DC`), `Partner_Edit_Documents`.  
ХП: `KI_FL4_id_Fill`, `KI_FL5_prevId_Fill`, `KI_History_Fill`.

Чтобы старый паспорт не вернулся: `forDel` в `Partner_Edit_Documents`, удалить из `KI_History_FL4`.

**Удаление** паспорта через 3.1: в XML только блок `current` с данными, которые убираем; в `title` неверный паспорт **не** указывать.

### FL6 / FL7 — ИНН / СНИЛС

Сверка: заявление, кнопка ФНС, ОВиА. Удаление СНИЛС/ИНН — кнопка «нет» на форме.

```sql
SELECT TOP 100 * FROM CZ_BKI.dbo.KI_FL6_tax WHERE keyRec IN (53147, 53148)
SELECT TOP 100 * FROM CZ_BKI.dbo.KI_FL7_socialId WHERE keyRec IN (53147, 53148)
SELECT TOP 100 p.INN, p.SNILS, * FROM dbo.Partner p WHERE p.keyPart = …
```

Событие 3.1 по этим блокам выглядит одинаково (разные имена блоков).

### FL8 / FL9 — адреса

Авто-3.1 капризный; условия в `KI_Correct_Fill`.  
Регистрация — вкладка паспорта, факт — «Дополнительно».

Чтобы событие собралось, должны отличаться **индекс или квартира** (как в примере Word).

Таблицы: `KI_FL8_address`, `KI_FL9_factAddress`, `Partner_Edit_Address`. Некорректным — `forDel` или правка нужной строки. ХП: `KI_FL8_address_Fill`, `KI_FL9_factAddress_Fill`.

### FL10 — телефон и почта

Авто-3.1 **нет**. Выгрузка (по договору удобны даты закрытия/прекращения, меньше событий) → вытащить XML → скопировать `Subject_FL` выше существующего → в верхнем очистить `Events` и вставить ручной 3.1 (примеры телефона/почты в Word).

Обязательно:

- перенумеровать все `orderNum` (3.1 = 1, дальше 2, 3…);
- в шапке `subjectsCount` = число `Subject_FL`;
- `groupBlocksCount` = число событий (`orderNum`).

`phoneComment` — только если комментарий относится к этому номеру. Телефон и почта в одном 3.1: сначала `Phone_group_FL_10_Contact`, затем `email`.
